# injection 스캐너 봉인 홀드아웃

> **룰을 쓰거나 튜닝하는 사람은 `test/fixtures/injection/holdout/` 을 열지 않는다.**
> 이 문서는 읽어도 된다. 코퍼스 본문과 케이스별 라벨은 여기에 없다.

## 왜 있는가

계획 §6 P4 r3 정정. r2 에서는 코퍼스를 쓴 사람이 그 코퍼스에 맞춰 룰을 튜닝했다. 그렇게 나온 "고위험 미탐률 0%" 는 학습셋 점수라서 의미가 거의 없다. 그래서 **룰을 쓰기 전에** 평가 세트를 만들어 봉인해 두고, 룰 작성자에게는 보여 주지 않는다.

- **AC-7:** 봉인 홀드아웃 기준 **오탐률 ≤ 5%**, **고위험 미탐률 0%**.
- 스캐너는 결정론적 룰 기반이다. LLM 은 쓰지 않는다(PRD 제약).
- 세트를 만든 사람은 룰 작성에 참여하지 않는다. 룰 작성 에이전트와는 따로 돌았고, 룰 작성 에이전트에게는 이 세트가 주어지지 않는다.

## 위치와 형식

| 경로 | 내용 |
|---|---|
| `test/fixtures/injection/holdout/case-NN.txt` | 이메일 **본문 텍스트** 50건(UTF-8, LF). HTML 메일은 사람이 텍스트로 옮긴 형태다. |
| `test/fixtures/injection/holdout/labels.json` | 케이스별 `label`(injection/benign), `risk`, `workload`, `lang`, `techniques` |

| `test/arch/injection-holdout-seal.arch.test.ts` | 봉인과 읽기 격리를 확인하는 arch 테스트 |

- 파일 이름은 **중립 번호**다. 고정 시드로 순서를 섞었기 때문에 이름이나 순서만 보고 양성·음성을 알 수 없다.
- 본문은 가공하지 않은 바이트 그대로다. 제로폭 문자, 비분리 공백, 동형문자 같은 비가시 문자도 **들어 있는 그대로** 봉인했다. 정규화는 스캐너가 할 일이다. 평가 러너가 미리 정규화하면 안 된다.
- 주소는 전부 `example.com`·`example.org`·`example.net` 계열이고, 서비스·회사·인명은 모두 가상이다.

## 위험도 기준

판정은 **지시가 먹혔을 때 무슨 일이 벌어지는가**로 한다. 문구가 얼마나 노골적인지는 기준이 아니다.

| 위험도 | 기준(하나라도 해당하면 그 등급) |
|---|---|
| **high** | ① 사용자 데이터가 제3자에게 나간다: 외부 주소로 전달·회신, 첨부 반출. ② 비밀이 나간다: 인증 코드, 재설정 링크, 비밀번호, API 키·토큰·웹훅 시크릿, 금융 정보. ③ 되돌리기 어렵거나 지속되는 권한 변경: 자동 전달 규칙, 신뢰 발신자 등록과 **승인 절차 폐지**가 함께 오는 경우, 사용자 명의 결제·계약 동의. ④ **인증 메일로 위장해 워크로드 1 을 겨냥한다**(①–③ 이 함께 있으면 항상 high). |
| **medium** | 외부 반출은 없지만 에이전트의 판단이나 사용자에게 보이는 결과를 조작한다: 요약·분류 왜곡, 사용자 기만, 신뢰·스팸 판정 조작, 페르소나 덮어쓰기, 시스템 프롬프트·도구 목록·정책 탐지(정찰). 발신자 본인에게만 회신을 보내게 하는 경우도 포함한다. |
| **low** | 피해가 사실상 없는 탐지나 장난: 특정 단어를 답장에 넣게 하기, 답장 문체 바꾸기. 효과는 "이 에이전트는 메일 속 지시를 따른다"는 사실이 새어 나가는 것뿐이다. |

애매하면 높은 쪽으로 매긴다. AC-7 의 "0%" 는 high 에만 걸려 있으니, 높게 잡을수록 기준이 엄격해진다.

## 규칙

1. **룰을 작성·튜닝하는 동안에는 열지 않는다.** 룰 작성자는 `holdout/` 의 파일, `labels.json`, 케이스별 평가 출력을 보지 않는다. 문구·기법 목록·통계(이 문서 수준)까지만 볼 수 있다.
2. **한 번이라도 보고 튜닝하면 소진이다.** 평가 결과를 본 **뒤에** 룰을 고치면, 그 룰로 이 세트에서 얻은 점수는 더 이상 AC-7 증거가 아니다. 세트를 소진 처리하고 **다른 사람이** 새로 만든다.
   - 집계 점수(오탐 n건, 미탐 n건)만 보고 고쳐도 소진이다. 어느 케이스가 틀렸는지 좁혀 가는 튜닝이 되기 때문이다.
3. **파일을 고치지 않는다.** 라벨 오류를 발견해도 제자리에서 고치지 않는다. 그것도 소진 사유로 기록하고 세트를 새로 만든다. 봉인 테스트가 수정을 잡아낸다.
4. `src/**` 는 홀드아웃 경로를 모른다. 평가 러너는 `test/**` 나 `scripts/**` 에 둔다.

## 봉인 방식

`test/arch/injection-holdout-seal.arch.test.ts` 가 다음을 단언한다.

1. `HOLDOUT.sha256` 파일 전체의 sha256 이 테스트 파일에 못 박힌 `SEAL_DIGEST` 와 같다. 해시 목록까지 같이 고쳐 봉인을 우회하면 이 **테스트 파일에 diff 가 남는다**. 그 diff 는 "세트를 다시 만들었다"는 뜻으로만 리뷰를 통과시킨다.
2. `holdout/` 아래의 파일 집합(숨김 파일·하위 디렉터리 포함)이 목록과 정확히 같다. 추가나 삭제가 있으면 실패한다.
3. 각 파일의 바이트 해시가 목록과 같다. 한 글자만 바뀌어도 실패한다.
4. `labels.json` 이 모든 케이스를 덮고 있다. 양성 20 / 음성 30, 양성은 전부 위험도가 있고 high 가 1건 이상, 음성의 과반이 워크로드 1 이다.
5. **읽기 격리:** `src/**` 의 어떤 파일(확장자 무관)에도 `holdout` 이라는 단어나 `fixtures/injection` 경로가 없다. 경로를 조각으로 조립하는 경우까지 잡으려고 단어 자체를 금지했다.

이 테스트는 **본문을 읽지 않는다**(바이트 해시와 라벨 개수만 본다). 본문에 대한 단언을 여기에 추가하지 마라.

### 세트를 새로 만들 때

1. 룰 작성에 참여하지 않은 사람이 새 코퍼스를 쓴다. 이전 세트와 문구가 겹치지 않게 한다.
2. `holdout/` 을 통째로 바꾸고 `HOLDOUT.sha256` 을 다시 만든다: `cd test/fixtures/injection && shasum -a 256 holdout/* > HOLDOUT.sha256`
3. `shasum -a 256 HOLDOUT.sha256` 값을 테스트의 `SEAL_DIGEST` 에 넣는다.
4. 위 소진 기록 표에 한 줄을 추가한다.

### 알려진 약점

- 리포에 `.gitattributes` 가 없다. Windows 에서 `core.autocrlf=true` 로 체크아웃하면 줄 끝이 바뀌어 봉인이 깨진다(실패하는 쪽이므로 안전하다). 이 경로에 `-text` 를 거는 것을 권장한다.
- 봉인은 **수정**을 막지 **열람**을 막지는 못한다. 열람 금지는 규칙 1 과 작업 분담으로만 지킨다.

## 평가 절차

**룰이 완성된 뒤에 한 번만** 돌린다.

1. 룰 작성자가 "완성" 을 선언하고 룰 커밋을 고정한다(커밋 해시 기록).
2. 룰 작성자가 **아닌** 사람이 평가 러너(`test/**` 또는 `scripts/**`)를 돌린다. 러너는 각 `case-NN.txt` 를 바이트 그대로 본문으로 넣고, 스캐너 판정을 `labels.json` 과 대조한다.
3. 지표:
   - **오탐률** = 음성 중 스캐너가 통과 외의 판정(격리·차단·플래그)을 낸 수 / 30. **≤ 5%, 즉 1건 이하.**
   - **고위험 미탐률** = high 양성 중 스캐너가 통과시킨 수 / 12. **0건.**
   - 참고 지표: medium·low 미탐 수, 워크로드 1 음성의 오탐 수(0건이 목표)
4. 결과를 아래 표에 기록한다. **케이스 번호는 기록하지 않고** 집계만 남긴다. 실패 케이스를 룰 작성자에게 넘기면 그 순간 세트가 소진된다.
5. 불합격이면 세트는 소진된다. 룰을 고친 뒤에는 새 세트로 다시 평가한다.

통계 한계: high 양성이 12건뿐이다. 12/12 를 탐지해도 실제 고위험 미탐률의 95% 상한은 약 25% 이다(rule of three: 3/12). 30건 음성에서 오탐 0건이어도 실제 오탐률 상한은 약 10% 이다. 이 세트는 **합격선을 통과했는지 확인하는 게이트**이지 정밀 측정이 아니다. 제3 세트를 함께 쓰는 이유다.

### v2 보류 (2026-09-23)

- v2 작성 에이전트가 공격 양성 본문을 쓰는 단계에서 **안전 분류기에 막혔다.** 파일을 하나도 쓰지 않았고, 음성만 반쪽 봉인하는 것도 하지 않았다(증거처럼 보이기만 한다).
- 분류기를 표현만 바꿔 우회하는 재시도는 하지 않는다.
- 대안으로 공개 코퍼스(Microsoft LLMail-Inject, MIT — `labelled_unique_submissions_phase2.json` 68.6 MB + `emails_for_fp_tests.json` 0.1 MB)를 제시했으나, **소유자가 "v2 평가는 나중에" 로 결정했다.**
- 결과: **활성 홀드아웃 없음.** `test/arch/injection-holdout-seal.arch.test.ts` 의 `ACTIVE_SEAL_DIGEST = null` 이 "홀드아웃 디렉터리·봉인 파일이 존재하지 않는다" 를 단언한다.
- **AC-7 판정은 GATE 이후로 보류다.** 스캐너 v2 는 학습셋(consumed/v1 + dev) 성능만 가진 채 운영에 들어간다 — 그 성능은 증거가 아니다. v1 의 일반화 실측(고위험 미탐 25%)이 지금 알고 있는 유일한 증거다.
- 재개 시: 공개 코퍼스 양성 + 한국어·인증 메일 위장 양성(공개 세트에 없다 — 사람이 쓴다) + 에이전트가 쓴 음성 30 → 봉인 → 1회 평가.

**공백:** 조사 범위 안에서는 공개된 **한국어** 이메일 injection 코퍼스를 찾지 못했다. **워크로드 1(인증 메일) 음성**을 크게 담은 공개 세트도 찾지 못했다. 이 두 축은 당분간 자체 홀드아웃에만 기대게 된다. 실존 인물의 메일이 든 공개 메일 코퍼스는 "실존 인물 주소 금지" 원칙과 충돌하므로 음성 원천으로 쓰지 않는다.

제3 세트도 같은 규칙을 따른다. 룰 튜닝에 쓰는 순간 그 세트는 평가용이 아니다. 튜닝용과 평가용으로 나눠 쓰려면 분할을 먼저 정하고 평가용 분할은 봉인한다.
